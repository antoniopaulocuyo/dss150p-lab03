# 10.6 — Backfill Reasoning

## Scenario
The DAG runs daily on schedule `0 2 * * *` with `catchup=False`. Suppose a
historical month (e.g. all of August 2026) needs to be reprocessed —
maybe the source files were corrupted that month and have since been
re-exported correctly.

## Why catchup=False changes the backfill story

With `catchup=False`, Airflow never automatically schedules missed past
runs — it only ever schedules the next run relative to *now*. This is the
right choice for this DAG (as noted in Task B) because each scheduled run
extracts and reprocesses whatever the *current* source files look like,
not a date-specific slice of data. There's no `WHERE order_date = {{ ds }}`
anywhere in the pipeline — `extract_sources()` copies the entire current
`orders.csv`/`products.json`/`customers.csv`, and `build_curated()` joins
the entire current dataset. So a "backfill" here doesn't mean the same
thing it would for a DAG that partitions its own extraction by execution
date.

## What backfilling actually means for this pipeline

Since the pipeline operates on the *whole current snapshot* of source data
rather than a date-partitioned slice, "backfilling August" is really one
of two different operations depending on what's actually needed:

1. **If the source files still contain historical August rows** (just
   maybe with corrected/re-exported values now) — the fix is simply
   running the DAG once, in `full` mode, today. The current
   `extract → transform → load` cycle will pick up the corrected records
   because they're still order rows sitting in the current `orders.csv`.
   No special "backfill" mechanism is needed — this pipeline's `load`
   already reprocesses the entire curated dataset every full run, and the
   `record_hash`-guarded UPSERT means only rows whose business content
   actually changed get rewritten. This is naturally idempotent: running
   it once, or running it five times, produces the same end state.

2. **If instead the goal is to reload just the August partition** from
   already-partitioned Parquet data (Goal 3's `data/partitioned/` output)
   — that's exactly what `run_mode=partition` with `year=2026, month=8`
   is for. This is the more literal "backfill a specific month" case, and
   the DAG already supports it directly via its existing params — no new
   code needed, just triggering the DAG with those config values.

## Idempotency is what makes either approach safe

Both paths rely on the same property verified throughout Goals 2–4: every
load operation is keyed on `order_id` via `ON CONFLICT ... DO UPDATE`, so
re-running the same logical data through the pipeline any number of times
converges to the same end state rather than duplicating rows. This is
precisely why a "backfill" isn't dangerous here the way it can be for
pipelines that do `INSERT`-only appends per run — without idempotent
UPSERT semantics, backfilling by re-triggering old runs would double- or
triple-count every row each time it was replayed. Because the load path
is UPSERT-based and guarded by `record_hash`, replaying the same day's
(or month's) data any number of times is always safe.

## If this DAG needed true date-partitioned extraction (future improvement)

If the source system ever changes so that `orders.csv` only ever contains
"yesterday's" rows (rather than the full historical dataset every time),
this pipeline's extraction step would need to become date-aware — e.g.
`extract_sources(run_id, data_interval_start, data_interval_end)` filtering
the source by date. At that point, `catchup=True` (or a manual
`airflow dags backfill` command specifying the date range) would become
meaningful, since each run's `{{ ds }}` would correspond to a genuinely
different, non-overlapping slice of data. Under the current design — full
snapshot extraction every run — catchup and date-ranged backfills wouldn't
add value and would just mean reprocessing the same current data multiple
times under different logical dates, which is more confusing than useful.
